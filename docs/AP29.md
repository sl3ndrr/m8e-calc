## Fehler und Routingvertrag

Auf dem Ausgangsstand wird `build-info.json` nach dem PWA-Precache erzeugt.
Ein normaler Fetch geht deshalb ins Netz; eine Navigation mit aktivem Worker
bekommt jedoch das gecachte `index.html`. Ein HTTP-200 und eine erreichbare
URL sind damit kein Buildnachweis. Ein erstmaliger unkontrollierter Aufruf
prüft diesen Fehler nicht.

Der generierte Produktionsworker folgt jetzt diesem Vertrag. Die Pfade sind
relativ zum konfigurierten Base-Pfad, standardmäßig `/m8e-calc/`.

| Anfrage                                                                  | Behandlung                                                                                                                     |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| Andere Origin, Methode ungleich GET oder außerhalb Base                  | Kein Eingriff des Workers                                                                                                      |
| Exakt `build-info.json`, mit beliebiger Query, als Navigation oder Fetch | Ausschließlich `fetch(request, { cache: 'no-store' })`, vor jedem Cachezugriff; weder SW- noch HTTP-Cache, keine Ersatzantwort |
| App-Einstiege Base und `index.html`, auch mit Query/Hash                 | Bestehendes Cache-first; nur diese Dokumentnavigationen dürfen die gecachte App-Shell verwenden                                |
| Exakte Pfade aus dem Produktions-Precache                                | Bestehendes Cache-first mit ignorierter Query/Vary, bei Cachemiss Netzwerk                                                     |
| Sonstige Pfade innerhalb Base, auch unbekannte Dokumente/JSON-Dateien    | Kein Eingriff; tatsächliche Serverantwort oder Netzwerkfehler                                                                  |

`build-info.json` bleibt explizit aus den Precache-URLs ausgeschlossen, auch
bei später geänderter Pluginreihenfolge. Das passive Plugin läuft weiterhin
nach dem PWA-Plugin. Die App fordert den Nachweis nicht an und erhält keine
Entwickleranzeige. Schema 1, Ziel `normal`/`gallery` und `sourceCommit: null`
ohne gültiges `GITHUB_SHA` bleiben erhalten. Installation, vollständiger
Asset-Precache, Waiting, Updateangebot, `SKIP_WAITING`, Controllerwechsel und
Bereinigung alter app-/base-spezifischer Caches bleiben unverändert.

## Reproduktion und Browserregression

```sh
npm ci
npm run check
npx playwright install --with-deps chromium firefox webkit
npm run test:e2e:provenance -- --reporter=list,json
```

Die separate AP29-Konfiguration führt in Chromium, Firefox und WebKit den
neuen Fall sowie sämtliche bestehenden Comfort- und PWA-Updatefälle aus.
Der Default-Chromiumlauf ignoriert nur den neuen Fixturefall; die bestehenden
PWA-Fälle bleiben auch in der normalen CI-/QA-Matrix aktiv.

Der globale Setup baut mit Vite vier vollständige Produktionsartefakte unter
`test-results/ap29-builds/`: A, B, normalen Build ohne CI-Kontext und Galerie
jeweils mit eigener Manifest-/Asset-/Worker-Erzeugung. A/B verwenden ausdrücklich
synthetische SHA-Fixtures (`aaaa…`/`bbbb…`) und einen nur im Test hinzugefügten
Meta-Marker im HTML. Dadurch unterscheiden sich HTML und Worker-/Cache-Identität.
Das sind keine behaupteten historischen Deployments. `check-build-target.mjs`
prüft alle vier Artefakte; derselbe Prüfer muss A bei erwartetem B zurückweisen.
Galerie wird separat erzeugt; `dist/` und das Pages-Artefakt bleiben normal.

Der Browser lädt zunächst A, wartet auf `serviceWorker.ready` **und** einen
aktivierten Controller und weist einen vorhandenen App-Cache nach. Ein zweiter
kontrollierter App-Tab hält Worker A auch während nativer JSON-/Fehleransichten
aktiv, sodass B den alten Cache nicht wegen fehlender A-Clients regulär aufräumt. Weder
App-Requests noch Precache dürfen den Buildnachweis enthalten. Anschließend:

1. Normalen Fetch und echte Dokumentnavigation im bereits kontrollierten Tab
   ausführen; Response und `schemaVersion`, `sourceCommit`, `target` als JSON parsen.
2. Einen alten A-Nachweis absichtlich in den SW-Cache schreiben. Ein separater
   unkontrollierter Tab außerhalb des Worker-Scopes wärmt außerdem den HTTP-Cache
   mit einer Stunde Frische. Chromium muss die Cachefüllung durch einen zweiten
   Fetch ohne weiteren Serverrequest bestätigen. Alle Browser protokollieren
   das tatsächliche Cacheverhalten; eine nicht cachefähige Headless-Session
   wird nicht als HTTP-Cache-Beleg ausgegeben. Dieser Tab ist ausschließlich Setup.
3. Server auf den separat gebauten Stand B umschalten. Die gecachte App zeigt
   weiterhin Marker A; ohne erzwungene Aktivierung muss der Nachweis bereits B
   liefern, per Fetch, Direktnavigation und Navigation mit Query. Ein zusätzlicher
   Serverrequest beweist, dass die direkte Navigation nicht aus altem Cache stammt.
4. Unbekannte technische Navigation als echten 404 prüfen, außerdem außerhalb
   Base und POST unverändert vom Server beantworten lassen. Einstieg über
   `index.html` mit Query und wissenschaftlichem Hashlink bleibt funktionsfähig.
5. Den tatsächlichen Test-Origin schließen und zusätzlich Browser-Offline setzen.
   Danach denselben normalen Fetch und dieselbe Direktnavigation versuchen:
   Netzwerkfehler oder echter HTTP-Fehler sind erlaubt; Status 200 mit App-Shell
   oder altem Nachweis wird abgelehnt. Der alte Cacheeintrag ist dabei vorhanden.

Der Server liefert reale gebaute Dateien; keine Page-Routenmocks, kein
abgeschalteter Worker und kein bloßer Textvergleich des Plugins. Anlagen
`navigation-a/b` und `provenance-evidence` enthalten Antworten, Controller,
Cache-URLs, Serverrequests, Browserversion und Offlinefehler; `checks.json`
enthält die vier Buildprüfungen sowie die verworfene A-als-B-Prüfung.
Die bestehenden Updatefälle prüfen ergänzend je vier Startmodi, tatsächliches
Waiting/Updateangebot/Aktivierung/Reload/Cachecleanup und alle vier Modi offline.

## Deployment abgleichen und Grenzen

Die vollständige Anleitung steht in [RELEASE.md](RELEASE.md). Einen online
geparsten Nachweis nur dann dem erwarteten Deployment zuordnen, wenn Schema 1,
Ziel `normal` und **vollständiger** `sourceCommit` mit dem Build-/Pages-SHA
übereinstimmen. Ein anderer Commit oder `null` bestätigt diesen Stand nicht.
CI kann einen synthetischen PR-Merge-SHA bauen; dieser ist vom Branch-Head und
vom späteren Pages-Build-SHA zu unterscheiden.

Build-Info identifiziert die vom Server ausgelieferten Buildmetadaten. Eine
noch aktive ältere App kann weiterhin aus ihrem SW-Cache stammen; das ist kein
Beleg, dass der sichtbare Tab bereits den Serverstand benutzt. Das Updateangebot
explizit annehmen und die konkrete UI separat prüfen. Ebenso ist die Datei kein
kryptografischer Integritätsnachweis aller Assets. Hosting/CDN müssen konsistente
Deployments ausliefern; `no-store` umgeht Browsercaches, aber repariert keine
falsch veröffentlichte oder zwischengeschaltete Serverantwort. Ein alter bereits
installierter Worker erhält die Korrektur erst nach seinem regulären Update.

AP29 prüft Produktionsbuilds auf CI-Preview/localhost. Kein bestandener Live-
Abruf oder eine interaktive Pages-Abnahme wird daraus abgeleitet. Live-Abnahme
und physische Browser-/Installationsabnahmen bleiben getrennt offen (#22).
Kein Merge, Release, Tag oder Live-Deployment wird durch diesen PR ausgeführt.
